## 0. 术语与名词规范（统一口径）

- RevealCard（揭示正面）：统一替代 FlipCard。含义为“通过移除/透明化卡背覆盖层来展示卡牌正面”，不涉及 3D 翻转动画。
- Cover Layer（覆盖层/卡背层）：位于卡牌正面上方的可交互层，控制是否可见以“揭示”卡面。
- Core（核心功能）：抽牌、展示、AI 解读及必要的状态与缓存。
- Non-core（非核心功能）：关于、历史记录、主题切换等，均延后到核心稳定后。
- 单一真相来源（SSOT）：一次抽牌会话的数据由 drawStore 持有，页面仅消费，不重复派生与复制。

说明：如产品文档出现“FlipCard”等旧术语，实施阶段统一理解为上述新术语，后续在产品文档中做一致性修订。

## 1. 目标与范围

- 目标：在保证核心功能优先（抽牌、展示与 AI 解读）的前提下，交付性能稳定、易维护、可测试的前端应用。
- 范围：UI 组件、状态管理、数据与服务封装、AI 解读集成、缓存策略、构建与部署、测试与可观测性。
- 不在本期：复杂 3D 翻转动画、非核心页面（关于、历史记录等）延后至核心功能稳定后处理。

## 2. 技术栈与环境规范

- 前端框架：Vue 3.5+
- 构建工具：Vite 7+
- 语言与语法：TypeScript（必选，严格模式）
- 状态管理：Pinia 3+
- 网络：Axios（或基于 fetch 的轻封装）
- 单元测试：Vitest（覆盖 stores、services、纯函数）
- 组件测试：@vue/test-utils（核心交互组件）
- 代码质量：ESLint + Prettier（与 Vite/Vue 官方推荐规则对齐）
- 运行要求：Node 20.x LTS（通过 Homebrew 安装并保持一致）；package.json engines：{"node":" >=20 <21"}
- 包管理器：npm（统一使用，不混用多包管理器）
- 模块别名：@ 指向 src 根（在 tsconfig.paths 与 Vite resolve.alias 同步定义）

- 开发环境准备（Mac + Homebrew）：
  1. 使用 Homebrew 安装 Node 20：
     - 安装命令：brew install node@20
     - 链接为默认 node（如有需要）：brew link --overwrite --force node@20
     - 验证：node -v（应为 v20.x），npm -v
  2. 项目依赖安装：npm ci（保证与 package-lock.json 一致）
  3. 常用脚本（将在工程基座 PR-1 中提供）：
     - npm run typecheck（vue-tsc --noEmit）
     - npm run lint / npm run format
     - npm run test
     - npm run build

## 4. 配置与环境变量（前端与后端分离）

- 注入位置与原则：
  - 前端仅注入非敏感变量，通过 `import.meta.env` 读取
  - 敏感密钥（如 `GEMINI_API_KEY`）仅在后端项目（Serverless / Vercel）配置
- 前端变量：
  - `VITE_AI_DEV_PROXY`：开发是否启用本地代理（1 启用，0 关闭）
  - `VITE_AI_BASE_URL`：后端基座地址，例如 `https://tarot-backend.vercel.app`
  - `VITE_GEMINI_MODEL`：模型选择（非敏感，可前端注入）
  - `VITE_APP_VERSION`：应用版本号（用于缓存失效）
- 后端变量（Vercel Dashboard 配置）：
  - `GEMINI_API_KEY`：Gemini API 密钥（敏感，仅后端）
  - `AI_PROXY_TIMEOUT_MS`、`GEMINI_MODEL`、`ALLOWED_ORIGINS` 等运行参数
- 环境文件：
  - 前端：`.env`（通用）、`.env.development`、`.env.production`、`.env.local`（本地私有）
  - 后端：Vercel 项目环境变量（不写入仓库）
- 安全：
  - 生产环境禁止在前端注入任何密钥；所有 AI 请求通过后端路由承接
- 使用示例：

```
const AI_BASE_URL = import.meta.env.VITE_AI_BASE_URL
const MODEL = import.meta.env.VITE_GEMINI_MODEL || 'gemini-1.5-flash'
```

## 5. 样式系统与设计令牌

- 技术：原子化需求不强，采用 CSS 变量 + BEM/约定式命名
- 设计令牌：在 src/styles/tokens.css 定义常用变量
  - 颜色：--color-bg, --color-text, --color-accent, --color-border
  - 间距：--space-1(4px), --space-2(8px), --space-3(12px), --space-4(16px), --space-6(24px)
  - 圆角：--radius-sm(6px), --radius-md(10px)
  - 阴影：--shadow-sm, --shadow-md
  - 动画时序：--duration-fast(120ms), --duration-base(200ms), --easing-cubic(cubic-bezier(.2,.8,.2,1))
  - 层级：--z-card(1), --z-cover(2), --z-modal(100)
- 可访问性：
  - 使用 :focus-visible 提供清晰聚焦环（避免禁用 outline）
  - 支持 prefers-reduced-motion：在此情况下缩短或移除过渡
- 响应式：
  - 断点：sm(360), md(768), lg(1024)
  - 卡牌网格在 sm 单列、md 双列、lg 三列（可按产品调整）

## 6. 数据模型与一致性

- Card：{ id: string, name: string, imageUrl: string, uprightMeaning: string, reversedMeaning?: string, arcana: 'Major'|'Minor', suit?: 'Wands'|'Cups'|'Swords'|'Pentacles', number?: number }
- Deck：{ id: string, name: string, cards: Card[] }
- Spread：{ id: string, name: string, positions: string[] }
- DrawResult：{ id: string, spreadId: string, selectedCards: Array<{ position: string, cardId: string, reversed: boolean }>, createdAt: number }
- AiInterpretation：{ drawId: string, summary: string, details: string[], tokens: number, cost: number, createdAt: number }
- 说明：落地以 /doc 下产品与 API 文档为裁决依据，如字段差异以产品规划为准并在此同步修订。

## 7. 状态管理（Pinia）

- stores/deckStore：
  - state：decks: Deck[]; spreads: Spread[]; loaded: boolean; version: string
  - actions：loadStaticDecks, loadFromApi, getCardById, getSpreadById
  - getters：allCards, majorArcana, minorArcanaBySuit
- stores/drawStore（单一真相来源）：
  - state：currentDraw: DrawResult | null
  - actions：startDraw(spreadId)、selectCard(position, cardId, reversed)、reset()
  - getters：isCompleted（selectedCards 是否与 positions 等长）
- stores/aiStore：
  - state：byDrawId: Record<string, AiInterpretation>
  - actions：fetchOrGetCached(drawId)
- 约束：
  - 组件只通过 actions 触发副作用，不直接改写 state
  - key 前缀：缓存持久化键为 tarot2:\*（如 tarot2:deckVersion、tarot2:draw:<id>）

## 8. 服务层设计与契约

- services/http（axios 实例）：
  - baseURL：VITE_TAROT_API_BASE_URL
  - 超时：8s；重试：网络错误最多 2 次，退避 300ms
  - 错误映射：统一抛出 { code, message }，避免组件处理底层细节
  - 取消请求：支持 AbortController（或 axios cancel token）
- services/tarotApi：
  - getAllCards(): Promise<Card[]>
  - getSpreads(): Promise<Spread[]>
  - getRandomCards(params: { count: number }): Promise<Card[]>
- services/gemini：
  - interpret(draw: DrawResult, cards: Card[], options?): Promise<AiInterpretation>
  - 前端通过后端路由调用：`POST ${VITE_AI_BASE_URL}/api/ai/gemini/generate`
  - 不在前端读取或携带任何密钥；提示词模板、温度、最大 token 等由后端统一控制
- services/cache：
  - get(key): T | null; set(key, value, ttlMs?): void; remove(key): void; clear(prefix?): void
  - 默认 TTL：会话存活；可为 AI 结果设定 24h；版本变更或明确操作触发强制失效

## 9. 组件与交互规格（核心）

- RevealCard（揭示卡）：
  - props：
- - card: Card（必填）
- - revealed: boolean（默认 false）
- - disabled?: boolean（默认 false）

* - frontSrc: string（必填，卡面图片）
* - backSrc?: string（默认 /assets/images/card_back.svg）
* - revealed: boolean（受控状态，默认 false）
* - disabled?: boolean（默认 false）
* - alt?: string（卡面可访问描述，揭示后使用）

- 结构：
- - 下层：卡牌正面（img 或背景图）
- - 上层：卡背覆盖层（/assets/images/card_back.svg），初始可见

* - 下层：卡牌正面（img 或背景图，aria-hidden="true"，揭示后移除）
* - 上层：卡背覆盖层（覆盖层在上，初始可见，z-index 高于卡面）

- 行为：
- - 点击/Enter/Space：如果未禁用，则触发 reveal；动画为 opacity 从 1 → 0，过渡时长 var(--duration-base)，结束后 pointer-events: none

* - 点击/Enter/Space：若 !revealed && !disabled 则触发 reveal；仅对覆盖层做透明过渡（opacity:1→0），过渡时长 var(--card-reveal-duration, var(--duration-base))，结束后 pointer-events: none；禁止 3D 翻转

- 事件：onReveal()（首次揭示时触发）
- - 无障碍：role="button"，tabindex=0，aria-pressed 表示是否已揭示

* - 无障碍：role="button"，tabindex=0；揭示前卡面区域 aria-hidden，揭示后可选 aria-live="polite" 提示；aria-pressed 表示是否已揭示
* - CSS 变量：--card-overlay-z（覆盖层层级，默认 2）、--card-radius、--card-shadow、--card-reveal-duration

- CardGrid（网格）：
- - props：cards: Card[]; columns?: { sm:1, md:2, lg:3 }；gap 使用设计令牌
- - 行为：键盘导航顺序与视觉顺序一致

* - CardGrid（网格）：
* - props：
* - cards: Array<{ id: string; frontSrc: string; alt?: string }>
* - columns?: { sm:number, md:number, lg:number }（默认 { sm:1, md:3, lg:5 }）
* - disabledIds?: string[]（可选）
* - 行为与 A11y：
* - Tab 顺序与视觉顺序一致；v1 暂不支持方向键（ArrowUp/Down/Left/Right）在网格内移动，后续版本评估后纳入
* - 占位与加载：卡面懒加载；卡背先可视，确保“不提前暴露”
* - CSS 变量：--grid-gap、--grid-max-width（断点可覆写）

- DeckSelector/SpreadSelector（若在 Phase B 引入）：
  - 简化为下拉或按钮组；非核心期可暂以固定牌阵

## 12. AI 解读与日志门控（Hedge 竞速）

说明：AI 解读流程支持 Hedge（两路并发竞速，择胜者），为保证开发期与测试期的稳定性，日志输出遵循阈值门控策略。

- Hedge 配置（前端环境变量，统一由 `readHedgeConfig()` 解析）：
  - `VITE_AI_HEDGE_ENABLED`：是否启用竞速（默认开启）
  - `VITE_AI_HEDGE_DELAY_MS`：第二路起跑延迟（毫秒，默认 120）
  - `VITE_AI_ABORT_LOSER`：胜者确定后是否中止败者（默认 true）
  - `VITE_AI_HEDGE_LOG_LEVEL`：日志阈值（`debug` | `info` | `warn` | `error`，默认 `warn`）

- 日志门控原则：
  - 事件发布：仅当事件级别 ≥ 阈值时才发布/捕获（用于测试计数与可观测性）。
  - 诊断日志：`readHedgeConfig` 在开发模式仅于 `debug` 级别输出诊断（`console.debug`），避免干扰用例。
  - 远程卡组拉取失败（开发模式）：当阈值为 `info` 时将此类非关键路径的告警降级为 `info`，在其他阈值维持 `warn`，既保证排障，又避免测试噪音。

- 错误分类与重试策略（服务层统一）：
  - 错误类型：`TIMEOUT` / `NETWORK` / `HTTP` / `CANCELLED`，由 `classifyError()` 归一化。
  - 重试策略：指数退避（起始延迟 300ms），可重试错误在允许范围内自动重试。
  - 取消语义：业务主动取消（如超时/用户取消）使用 `AbortError` 并标记 `CANCELLED`，开发模式下使用 `console.info` 记录（避免误报为故障）。

- 流程摘要（两路并发，择胜者）：
  1. 读取 Hedge 配置，路由两路（Gemini / Zhipu），第二路按 `delayMs` 延迟起跑。
  2. 任一路先返回且解析成功即为“胜者”，在 `abortLoser` 为 `true` 时立即中止另一方。
  3. 胜者与败者的事件按阈值发布；在总超时或两路均失败时回退本地 Mock。

测试约束：
- 所有自动化测试的期望以本技术文档为准，不为迎合既有代码而降低标准；发生偏差时先修正实现再更新测试。

## 13. 构建与部署

- 构建：Vite 默认生产配置，生成 dist 静态资源
- 资源：图片走 Vite 资源管线；SVG 按需内联或文件引用
- TypeScript：构建前执行 `vue-tsc --noEmit`，类型错误阻止构建
- 部署：
  - 任意静态托管（Nginx、Netlify、Vercel 等）
  - HTTP 压缩（gzip/br）与缓存（静态资源带哈希强缓存）
  - 静态资源（卡牌图片）处理：通过 Vite 的 import.meta.glob 在 src/utils/images.ts 建立资源索引，构建时打包到 dist/assets；运行时一律使用 getCardImagePath/attachFrontSrc 获取 URL，严禁字符串拼接路径；卡背 back.svg 作为兜底（生产环境不打印敏感日志）
- 环境：通过环境变量注入 API 基址与开关

- CI 规范（最小闭环）：
  - 触发：每个 PR → dev，以及 dev 合并到 main 前
  - 步骤（必须全部通过）：
    1. npm ci
    2. npm run typecheck（vue-tsc --noEmit）
    3. npm run lint
    4. npm run test
    5. npm run build
  - 钩子（本地保障）：pre-commit 运行 lint-staged；pre-push 运行 typecheck + test
  - 门禁：检查未通过不得合并；合入 main 需你确认
  - CD：暂不自动化，Phase A 稳定后按你指定的平台接入

### 13.1 部署拓扑选型（汇总）
- 方案 A（推荐、简单稳妥）
  - 前端：Public 仓库 + GitHub Pages/Cloudflare Pages（仅静态资源，不含密钥）
  - 后端：Private 仓库 + 海外区域的运行平台（如 Cloud Run/Render/Fly.io/Cloudflare Workers）
  - 前端只调用你的后端域名；后端代理第三方（Gemini/Tarot 等），统一做鉴权、重试、限流与错误处理
- 方案 B（同平台一体化）
  - 前端：Cloudflare Pages
  - 后端：Cloudflare Workers/Pages Functions（Secrets 存放在平台）
  - 优点：同平台内通信/加速、低运维成本、默认不暴露密钥
- 方案 C（面向国内用户优先）
  - 前端：国内 CDN（阿里云 OSS+CDN/腾讯云 COS+CDN）
  - 后端：部署在香港/新加坡等可直连 Gemini 的区域；或接入国内模型（后端留“模型适配层”）
  - 结合域名与缓存减轻跨境延迟

### 13.2 仓库与权限策略
- 前端仓（Public）：
  - 开启主分支保护：禁止直接 push，仅通过 PR 合并；至少 1 次 Code Review + CI 全绿
  - 部署凭据最小权限：仅读权限、仅限目标仓库；启用 2FA
  - 禁止来自 Fork 的 PR 访问 CI Secrets；外部 PR 使用受限流水线
- 后端仓（Private）：
  - 存放实现细节与 CI/CD 配置，集中管理 Secrets；降低攻击面并满足审计/合规
  - 即使后端部署在第三方平台，私有仓仍是供应链管理与版本回溯的基座

### 13.3 密钥与安全（Gemini 等）
- 原则：密钥从不下发至前端；仅存放于后端或平台 Secret 管理（环境变量/密钥服务）
- 风险：泄露将导致配额被薅、潜在扣费、违规滥用与账号封禁；即使免费套餐亦会影响服务可用性与信誉
- 措施：
  - 统一走后端代理；前端只访问你自有后端域名
  - 分环境密钥（dev/staging/prod）与定期轮换；开启预算/用量告警
  - 若支持来源/IP 白名单则开启限制（视服务商能力）
  - 疑似泄漏时：立即停用/轮换，审计用量并回收权限

### 13.4 区域与外网连通性
- 海外区域（如新加坡/东京/硅谷等）默认可访问 Google 生态，能直连 Gemini
- 中国大陆区域云主机通常无法直连 Google 相关域名，后端若在大陆区则无法调用 Gemini
- 解决：
  - 将后端部署在可直连的海外区域；或为国内用户切换到国内合规模型
  - 前后端分离后，用户仅需访问你的前端/后端域名，不必直连第三方；“能否访问外网”由后端负责

### 13.5 Tarot API 与 AI 路由
- Tarot API：当前公共接口无需密钥，且内置本地数据作兜底；可在生产通过后端统一转发并做缓存
- AI（Gemini）：生产一律经后端代理；在后端做重试、熔断、限流与内容安全过滤

### 13.6 阶段性决策（当前 → 生产）
- 当前阶段（功能验证/MVP）：沿用现有前端实现验证核心流程；保留失败回退路径
- 生产阶段：切换“后端代理 + 前端 Public、后端 Private”的拓扑；密钥仅服务端持有；按 13.2/13.3/13.4 执行
- 任务落地建议：
  - 后端提供 POST /api/ai/analyze（服务端携带密钥调用 Gemini），返回标准化结果；开启 CORS 仅允许前端域名
  - 前端移除直接读取 Gemini Key 的逻辑，改为调用自有后端；失败回退保留
  - DevOps：海外区域部署、预算与用量告警、日志与指标监控、分支保护与 CI 门禁
